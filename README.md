# LLM Gateway (V1)

A backend service that acts as a **unified API gateway** between an application
and multiple LLM providers (OpenAI, Google Gemini, Anthropic Claude).

The application talks only to this gateway. The gateway hides each provider's
specific API behind a common interface, and centralizes authentication,
validation, usage logging, and error handling.

## What it does (V1)

- **Unified chat endpoint** (`POST /v1/chat/completions`) across providers.
- **Provider abstraction** — Gemini & Groq adapters behind one interface; adding a
  provider needs no changes to the gateway, routes, or schemas.
- **Model registry** — public aliases (`gemini`, `groq`, …) → provider + model.
- **API-key authentication** — clients send a gateway key; only SHA-256 hashes are
  stored (PostgreSQL).
- **Usage logging** — per-request metadata (model, provider, tokens, latency,
  status) persisted; never prompts or responses.
- **Request IDs** — one `X-Request-ID` per request, in logs, DB, and responses.
- **Standardized errors & timeouts** — consistent `{"error":{code,message}}`
  envelope; upstream calls are bounded by a configurable timeout.
- **React console** + **Docker Compose** one-command stack.

## Architecture

```
 Browser ──┬─► http://localhost:3000  frontend (nginx, static React bundle)
           └─► http://localhost:8000  backend gateway (FastAPI / uvicorn)
                        │
   request-id → auth → validation → model registry → GatewayService
                        │                                   │
                        │                          provider factory
                        │                         ┌─────────┴─────────┐
                        │                     GeminiProvider      GroqProvider
                        │                         │                   │
                        │                     Google API          Groq API
                        ▼
                 usage logging ─► PostgreSQL (users, api_keys, requests)
```

Provider API keys are used **only** by the backend to call providers. The gateway
API key authenticates **clients to the gateway** — see
[Two kinds of API keys](#two-kinds-of-api-keys).

## Backend: run locally (development)

Requires Python 3.12+.

```bash
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Then visit:
- Health check: http://localhost:8000/health
- Interactive API docs (auto-generated by FastAPI): http://localhost:8000/docs

## Run everything with Docker (recommended)

Runs PostgreSQL, the backend, and the frontend in three containers — no host
Python/Node/Postgres needed. Requires Docker (or colima) with Compose.

1. Create `backend/.env` from `.env.example` and add your provider keys +
   `GATEWAY_API_KEYS` (Compose injects the correct `DATABASE_URL` automatically).
2. Build and start:

```bash
docker compose up --build
```

- Frontend: http://localhost:3000
- Backend: http://localhost:8000 (docs at `/docs`)

The backend runs `alembic upgrade head` on startup. Seed a gateway key once:

```bash
docker compose exec backend python -m app.db.seed
```

Run the backend test suite inside the container:

```bash
docker compose exec backend pytest -q
```

Stop the stack (keep the database volume):

```bash
docker compose down
```

Stop and **delete** the database volume (fresh start):

```bash
docker compose down -v
```

## API endpoints

| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| GET | `/health` | none | Liveness check |
| GET | `/v1/models` | none | List public model aliases |
| POST | `/v1/chat/completions` | `Authorization: Bearer <gateway key>` | Chat completion |

Request body:

```json
{ "model": "groq", "messages": [{ "role": "user", "content": "Explain polymorphism" }] }
```

Errors use a single envelope with an `X-Request-ID` header:
`401 UNAUTHORIZED`, `404 UNKNOWN_MODEL`, `422 VALIDATION_ERROR`,
`502 PROVIDER_ERROR`, `503 PROVIDER_UNAVAILABLE`, `500 INTERNAL_ERROR`.

## Two kinds of API keys

| | Gateway API key | Provider API key |
|---|---|---|
| Example | `gw_...` | `GEMINI_API_KEY`, `GROQ_API_KEY` |
| Used by | the **client** → this gateway | the **gateway** → the LLM provider |
| Where it lives | sent by the browser/app as `Bearer`; stored **hashed** in Postgres | `backend/.env` only, never leaves the backend |
| In the frontend? | yes (typed by the user at runtime) | **never** |

## Provider configuration

Set in `backend/.env` (from `.env.example`). The app starts even if some keys are
missing — requests for an unconfigured provider return `503`.

| Variable | Meaning |
|---|---|
| `GEMINI_API_KEY`, `GROQ_API_KEY` | Provider credentials |
| `GEMINI_MODEL`, `GROQ_MODEL` | Override the model an alias maps to |
| `GATEWAY_API_KEYS` | Comma-separated client keys to seed (`python -m app.db.seed`) |
| `LLM_TIMEOUT_SECONDS` | Upstream timeout (default 30, must be > 0) |
| `DATABASE_URL` | Postgres URL (Compose injects the in-network value) |

## Frontend: run locally (development, without Docker)

A simple React + Vite console for exercising the gateway. Requires Node 18+.

```bash
cd frontend
npm install
npm run dev
```

Then open http://localhost:5173. In the UI, paste your **Gateway API key**
(the client key seeded via `python -m app.db.seed`, *not* a provider key),
pick a model, type a message, and Send.

The gateway base URL defaults to `http://localhost:8000`; override it by copying
`frontend/.env.example` to `frontend/.env` and setting `VITE_API_BASE_URL`.
`VITE_*` values are embedded in the browser bundle and must never hold secrets —
provider keys stay backend-only in `backend/.env`.
